# ADR 0002: 要約キャッシュと話題レイヤの設計

## Status

Accepted

## Context

Chronica を「AI に DB をコンテキストとして渡す」用途で使う場合、現状は生ログを引く設計しか無い。
同じ範囲を 2 回要約すれば 2 回 LLM を呼ぶことになり、コストと待ち時間が線形に増える。

実測では、1 チャンネル 1 か月分の本文が約 1 万文字（5 千トークン相当）、
全 27,797 件で約 306 万文字（153 万トークン相当）だった。
チャンネル×期間で切れば 1 回のリクエストに収まるが、**繰り返し要約する運用では再利用が要る**。

また話題の切れ目は主観を含む。機械が出した分割をそのまま正本にすると、
間違ったときに人が直せず、年代記として使われなくなる。

設計にあたり、独自の語彙を作らずに済むよう先行概念を調査した。

## Decision

### 1. 生ログと派生データを分ける（event sourcing + projection）

`messages` を append-only の**イベントログ**として扱い、要約・話題分割は
そこから**再構築可能な派生ビュー（projection）**として持つ。
派生を捨てても生ログから作り直せる状態を維持する。

`raw_json` に、専用列へ載せていない受信情報 (embeds / reactions / mentions 等) を残しているのは、
この再構築可能性のためである。専用列と重複する項目は保存しない (容量だけ増えるため)。

`medallion architecture`（bronze / silver / gold の 3 層）は採用しない。
単一 SQLite・数万件規模に対して語彙が過剰であり、`raw` / `derived` の 2 層で足りる。

### 2. 要約キャッシュは cache key derivation で無効化する

`summaries` テーブルを追加し、**入力範囲のハッシュ**をキーにする。
入力が変わっていなければ再利用し、変わっていれば作り直す。

これは LangChain の `SQLiteCache` が `(prompt, llm_string)` を複合キーにする設計、
および LlamaIndex の `IngestionCache` / `docstore_strategy` が
ドキュメントのハッシュ比較で未変更分をスキップする設計と同型である。

要約の要約を積む場合は **tree_summarize**（ボトムアップの再帰マージ）の形を取る。
「rollup」「fold」は一般語であり標準名ではないため、用語としては使わない。

### 3. 話題分割は silver / gold を分ける

機械が出した分割候補を **silver**、人間が修正した確定版を **gold** として別に持つ。
食い違いを人が裁定する工程を **adjudication** と呼ぶ。
これは corpus annotation の gold standard 慣行に沿った標準的な語彙である。

処理そのものは **topic segmentation**（会話特化では dialogue topic segmentation）と呼ぶ。
「確定トピック」「仮トピック」のような独自語は使わない。

初期実装ではチャンネルを粗い話題境界として扱い、チャンネル内の自動分割は行わない。
`topics` / `topic_messages` のスキーマだけ先に用意し、silver を埋める実装は後続とする。

## Consequences

**得られるもの**: 同じ範囲の再要約が不要になる。話題の修正が機械の再計算で消えない。
生ログを保持しているため、要約アルゴリズムを変えても過去に遡って作り直せる。

**払うもの**: テーブルが 2 つ増える。要約の入力範囲を一意に定める規則
（チャンネル + 期間、またはメッセージ ID 範囲）を決める必要がある。

**やらないこと**: 本 ADR は**スキーマとインタフェースまで**を定める。
実際に外部 LLM へ本文を送る実装は含めない。送信は利用者の明示的な設定を要する。

**将来の見直し条件**: 自動 topic segmentation を入れる際、
TextTiling 系の古典手法と BERT ベースの手法を比較して選ぶ。
その際も機械出力は silver に入れ、gold を上書きしない。

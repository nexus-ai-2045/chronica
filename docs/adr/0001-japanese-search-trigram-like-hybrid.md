# ADR 0001: 日本語検索は trigram + LIKE のハイブリッドにする

## Status

Accepted

## Context

Chronica は SQLite FTS5 の `tokenize='trigram'` で全文検索を実装している。
実データ 27,797 件で計測したところ、**2 文字の日本語クエリが 1 件もヒットしない**ことが分かった。

| クエリ | trigram | unicode61 | LIKE（期待値） |
|---|---:|---:|---:|
| 開発（2字） | 0 | 5 | 329 |
| 宇宙（2字） | 0 | 74 | 896 |
| AI（2字） | 0 | 513 | 2,198 |
| レビュー（4字） | 88 | 3 | 88 |
| ハッカソン（5字） | 262 | 13 | 262 |

これは実装の不具合ではない。SQLite 公式ドキュメントが trigram の仕様として明記している。

> Substrings consisting of fewer than 3 unicode characters do not match any rows
> when used with a full-text query.
> — [SQLite FTS5 Extension](https://www.sqlite.org/fts5.html)

代替として `unicode61` を試したが、**より危険**だった。0 件ではなく少数を返すため
検索が動いているように見えるが、「開発」で 329 件中 5 件しか返さない（98% 欠落）。
CJK には単語境界が無く、連続文字列を 1 トークンとして扱うためである。

日本語の語彙は 2 文字語（開発・要約・予算・宇宙）が非常に多く、
この制約は「深掘りの起点としての検索」を実質的に無効化する。

## Decision

**クエリ長で経路を分ける。**

- 3 文字以上 → FTS5 trigram（インデックス検索）
- 2 文字以下 → `LIKE '%q%'` による全表走査

これは独自の回避策ではなく、SQLite 公式が trigram の設計として示している挙動の応用である。
公式ドキュメントは、trigram インデックスが LIKE / GLOB の高速化にも使われること、
および非ワイルドカードの連続文字を含まないパターンでは全表走査にフォールバックすることを明記している。

`unicode61` および bigram 前処理は採用しない。前者は取りこぼしが大きく、
後者は漢字ランのみを bigram 化する「スクリプト認識型」の作り込みが必要で、
現時点の規模に対して複雑さが見合わない。

## Consequences

**許容できる**: 27,797 件での LIKE 全走査は **14.9 ms** で完了する（実測）。
体感上インデックス検索と区別がつかない。

**将来の見直し条件**: 10 万件を超えたあたりで LIKE の線形増加が体感に出る。
その時点で「漢字ランのみ bigram 化するスクリプト認識型トークナイザ」を再検討する。
件数が閾値を超えたことを検知できるよう、`export` 時に総件数を出力している。

**利用者への影響**: なし。クエリ長による経路の違いは UI に露出しない。
